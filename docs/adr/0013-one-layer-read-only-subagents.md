# 引入一层只读子 agent

## Status

accepted（推翻 ADR-0001「没有子 agent 的位置」这一条；单进程、单供应商、行式界面不变）

## 背景

`code-review` 技能要求把「标准」和「规格」两条评审线放进**两个互不可见的上下文**里并行跑：同一个上下文里先后跑，第二条线会看到第一条的结论，两条轴就互相污染了。仓库原本没有子 agent，这个技能在 yi 里无法按设计执行。

同时 repo 的硬约束是「一个项目一条会话、单进程、轻量」，omp 那套子 agent（独立子会话、`yield` 结构化交卷、`agent://` 寻址、后台收发、工作树隔离、模型角色）远超这个技能所需。

## 决定

- 新增第九个工具 `task`，参数只有 `task`（完整任务描述）和可选的 `name`（标签）。
- 子 agent 是**同进程线程**：独立消息历史、独立 Provider（换一个会话标识）、同一套供应商与模型；返回最终一段文本。
- 子 agent 的工具**固定只读**：`read`、`grep`、`glob`、`lsp`，加上计划模式那套只读 `bash` 白名单；没有 `write` / `edit` / `db_query` / `task`。
- 同一轮里的多个 `task` 并行执行，最多 4 个；只有一层，子 agent 不能再派。
- 不建子会话文件；结果作为父会话的一条工具结果落盘，中间过程写到会话目录下的 `logs/task-<调用 id>.log`。
- 结果截断到 400 行 / 16 KB；子 agent 最多 30 步，超了报错收尾。

## 考虑过的选项

- **子进程（`yi exec`）**：隔离最彻底，但要绕开「一个项目一个实例」的文件锁、处理并发与取消、每次重新加载提示词。否决。
- **改写 `code-review` 让两条轴顺序跑**：丧失独立性，违背技能的设计前提。否决。
- **照搬 omp 的完整子 agent**：结构化 `yield`、子会话、`agent://`、后台收发、工作树隔离。评审用不到，成本与维护面都大。否决。

## 影响

- 工具表从八个变九个；所有已有会话的请求前缀变一次（缓存重建一次）。
- 计划模式下 `task` 可用（子 agent 本来只读），但子 agent 不继承父对话历史。
- 子 agent 的 token 用量计入它自己的请求，**不**汇总到页脚的父轮用量；成本会体现在账单上，页脚看不到。
- 日志可能包含被评审代码的片段，落在会话目录下，随会话一起清理。
