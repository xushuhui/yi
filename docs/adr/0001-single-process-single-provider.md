# yi 是单进程、单供应商、线性会话的 Rust 终端 agent

## Status

accepted

## 背景

omp 在这台机器上跑着 15 个进程、合计约 1.5 GB 常驻内存，安装包 199 MB，会话数据 531 MB；而我的真实用量集中在五个工具（占 39,886 次工具调用的 90.7%）。同时它的会话模型要求我反复结束再新开，39 个项目攒出 181 个会话。yi 的目标是把我每天真正做的事做到最短路径，其余一律不做。

## 决定

1. **单进程、无异步运行时。** 一个 Rust 二进制，阻塞 IO 加线程和通道。否决 tokio：单人单会话的循环里它只增加依赖与心智负担。
2. **只接 DeepSeek 的 `deepseek-flash`。** 一个供应商一个模型，`/models` 实测上下文 1,048,576、输出上限 393,216、输入支持图片、推理强度仅 `low`/`high`/`max`。否决多供应商抽象：抽象的收益来自第二个供应商，而第二个供应商不会出现。
3. **会话是线性 JSONL，与项目一一对应，不存父子指针。** 否决 omp/pi 的树形条目：不做分支、fork、会话树，树形结构就是死重量。
4. **默认行为是继续，而不是新建。** 否决“默认新会话、用 `-c` 继续”：那会重现同一项目攒出十几个会话的老毛病。换新的唯一入口是 `/new`。
5. **直接依赖上限 6 个，按里程碑分批引入（里程碑 ① 只用 3 个，`cargo tree` 实测 33 个包）。** 否决 168 个包的主流栈（tokio + reqwest + clap + ratatui）；也否决一上来就引入 ratatui 与 crossterm（约 80 个包），界面先行式输出，理由见 ADR-0002。
6. **锚点编辑保留“只能改已读区间”。** 否决只校验内容哈希的宽松版（模型会凭想象改没读过的代码），也否决 pi 的原文唯一匹配（重复代码会卡死）。
7. **压缩阈值 50%、保留最近 20,000 token。** 否决 omp 的 35%：更早压缩意味着更频繁地打断前缀缓存，而缓存命中价只有未命中的五十分之一。

## 影响

- 没有扩展、钩子、MCP、子 agent 的位置；新能力只能进核心或不做。
- 系统提示词、工具定义、上下文文件在一次会话内不可变，换来前缀缓存稳定；改配置需要重启。
- 换供应商或换模型意味着改核心代码，而不是加配置——这是刻意的。
