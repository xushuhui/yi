# 领域文档

工程类技能在探索这个仓库时，按下面的规则消费领域文档。

## 探索之前先读这些

- 仓库根的 **`GLOSSARY.md`**
- 如果根目录存在 **`GLOSSARY-MAP.md`**，则按它指向的每个上下文各读一份 `GLOSSARY.md`（只读与当前主题相关的）
- **`docs/adr/`**：读与你要动的区域相关的 ADR。多上下文仓库还要看 `src/<上下文>/docs/adr/`

任何一份文件不存在就**静默继续**：不要报告缺失，也不要建议预先创建。它们由 `/domain-modeling` 技能（经由 `/grill-with-docs` 和 `/improve-codebase-architecture` 触达）在真正定下术语或决定时按需创建。

## 文件结构

单上下文仓库（绝大多数仓库）：

```
/
├── GLOSSARY.md
├── docs/adr/
│   ├── 0001-....md
│   └── 0002-....md
└── src/
```

多上下文仓库（根目录存在 `GLOSSARY-MAP.md`）：

```
/
├── GLOSSARY-MAP.md
├── docs/adr/                       ← 全局决定
└── src/
    ├── ordering/
    │   ├── GLOSSARY.md
    │   └── docs/adr/               ← 上下文相关的决定
    └── billing/
        ├── GLOSSARY.md
        └── docs/adr/
```

本仓库是**单上下文**。

## 使用术语表的词汇

当你的输出要命名一个领域概念（票据标题、重构提案、假设、测试名）时，使用 `GLOSSARY.md` 里定义的那个词，不要漂移到它明确标注「避免」的同义词上。

如果需要的概念还不在术语表里，那是一个信号：要么你在发明这个项目不用的语言（重新考虑），要么确实存在缺口（留给 `/domain-modeling` 处理）。

## 报告 ADR 冲突

如果你的输出与现有 ADR 相矛盾，明确指出来，不要悄悄覆盖：

> 与 ADR-0001（单进程、单供应商）冲突，但值得重开，因为……
